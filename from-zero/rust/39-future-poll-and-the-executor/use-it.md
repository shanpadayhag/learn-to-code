# Concept 39 · `Future`, `poll`, and the executor (who runs a paused function) — Use it

> Pair: **Use it** (you are here) · [Under the hood](under-the-hood.md)
> Track: [From-Zero: Rust](../README.md) · Previous: [Concept 38](../38-async-and-await/use-it.md)

## The idea
[Concept 38](../38-async-and-await/use-it.md) left one thing as a black box. You know that an
`async fn` builds a paused value and that `block_on` drives it, but not what "drive" means. That gap
is where the whole payoff lives, so open it.

A future is asked to make progress by calling one method on it, and it can give exactly two answers:

- **`Poll::Ready(value)`** — I'm finished, here's the result.
- **`Poll::Pending`** — I can't get further right now. Ask me again later.

That's it. A future is a value you poke repeatedly until it says it's done. An **executor** is the
ordinary, non-async loop that does the poking.

And here is the part worth reading twice: *if the loop is holding one future it drives one task, and
if the loop is holding two futures it drives two tasks — on the same thread, interleaved.*
Concurrency isn't something `async` gives you. It's something the **loop** gives you, and once you've
written the loop yourself you'll never confuse the two again.

## The trait, in full
`Future` is a normal [trait](../20-traits/use-it.md) from the standard library. Here it is, complete —
it has one method:

```rust
pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

Piece by piece:

- **`type Output`** — an associated type: what this future produces when it finishes. For
  `async fn brew() -> String`, `Output = String`.
- **`Poll<T>`** — an [enum](../14-enums/use-it.md) with two variants, `Ready(T)` and `Pending`. It's
  the same shape as [`Option`](../15-option/use-it.md) with names that say *time* instead of
  *absence*.
- **`Pin<&mut Self>`** — a `&mut self` carrying one extra promise: *this value will not move again*.
  A paused future can hold references to its own fields ([Concept 38](../38-async-and-await/under-the-hood.md#why-a-paused-future-may-not-move)),
  so moving it after polling would leave those references pointing at the old address. `Pin` is that
  rule made into a type.
- **`cx: &mut Context`** — carries a **`Waker`**, the callback a future uses to say *"I can make
  progress now, poll me."* Without it, an executor would have no idea when to try again and would
  have to spin.

## Write a future by hand
Every future you've used so far was generated by `async`. Write one yourself and the trait stops
being abstract — this one pauses a fixed number of times, then finishes:

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Pause {
    polls_left: u32,
}

fn pause(times: u32) -> Pause {
    Pause { polls_left: times }
}

impl Future for Pause {
    type Output = ();

    fn poll(mut self: Pin<&mut Self>, _context: &mut Context<'_>) -> Poll<()> {
        if self.polls_left == 0 {
            Poll::Ready(())
        } else {
            self.polls_left -= 1;
            Poll::Pending
        }
    }
}
```

That struct is the hand-written version of what the compiler builds for you: **state in the fields, a
decision in `poll`.** `polls_left` is the state tag. Counting down is the state transition. Once you
see that `async fn` is just a machine-generated `impl Future`, nothing about the feature is magic
any more.

Now it can be `.await`ed like anything else:

```rust
async fn steps(label: &str, count: u32) -> u32 {
    let mut done = 0;
    while done < count {
        pause(1).await;
        done += 1;
        println!("  {label} step {done}");
    }
    done
}
```

## Write the executor
`block_on` from the last lesson, now readable line by line:

```rust
fn block_on<F: Future>(future: F) -> F::Output {
    let mut future = pin!(future);                              // 1
    let mut context = Context::from_waker(Waker::noop());       // 2
    loop {
        match future.as_mut().poll(&mut context) {              // 3
            Poll::Ready(value) => return value,                 // 4
            Poll::Pending => {}                                 // 5
        }
    }
}
```

1. **`pin!`** parks the future at one address on this stack frame and hands back a `Pin<&mut F>`. It
   must happen before the first poll and it can never be undone — that's the promise the trait wants.
2. **`Waker::noop()`** is a waker that does nothing when called. Honest placeholder: this executor
   has nowhere to *be* woken to, so it will simply ask again immediately.
3. **`.as_mut()`** re-borrows the pin so the loop can poll more than once without giving it away.
4. **`Ready`** — done, hand the value out and stop.
5. **`Pending`** — do nothing and go round again.

Four lines of real logic. That is a complete, working async runtime for one task.

## The payoff: two tasks, one thread
Now change one thing — hold *two* futures in the loop instead of one:

```rust
fn run_both<A: Future, B: Future>(first: A, second: B) -> (A::Output, B::Output) {
    let mut first = pin!(first);
    let mut second = pin!(second);
    let mut context = Context::from_waker(Waker::noop());

    let mut first_output = None;
    let mut second_output = None;

    while first_output.is_none() || second_output.is_none() {
        if first_output.is_none() {
            if let Poll::Ready(value) = first.as_mut().poll(&mut context) {
                first_output = Some(value);
            }
        }
        if second_output.is_none() {
            if let Poll::Ready(value) = second.as_mut().poll(&mut context) {
                second_output = Some(value);
            }
        }
    }

    (first_output.unwrap(), second_output.unwrap())
}
```

The [`Option`](../15-option/use-it.md) per task is doing real work: a future must never be polled
again after it answers `Ready`, so "have I already got this one's answer?" is state the loop has to
keep. Run the same two tasks both ways:

```rust
async fn one_after_the_other() -> (u32, u32) {
    let a = steps("toast", 3).await;
    let b = steps("eggs", 2).await;
    (a, b)
}

block_on(one_after_the_other());
run_both(steps("toast", 3), steps("eggs", 2));
```

```text
sequential — .await one, then the other:      concurrent — poll both in one loop:
  toast step 1                                  toast step 1
  toast step 2                                  eggs  step 1
  toast step 3                                  toast step 2
  eggs  step 1                                  eggs  step 2
  eggs  step 2                                  toast step 3
```

Same tasks. Same single thread. No `thread::spawn` anywhere. The only difference is who holds the
loop — and that is the whole distinction between **async** and **concurrent**:

> **`.await` is sequential.** Inside one task it means "stop here until this finishes."
> **Concurrency comes from an executor polling several futures**, which is what `join!` and
> `tokio::spawn` do for you in real code.

If you take one thing from Phase 10, take that. The commonest async bug in every language is writing
two `.await`s in a row and expecting them to overlap.

## What a real runtime adds
Your `block_on` is correct and unusably wasteful: with a no-op waker it re-polls at full speed,
burning a core to ask "done yet?" a million times a second. Real runtimes — `tokio`, `async-std`,
`smol` — keep the exact shape you just wrote and fix that one thing:

| your loop | a real runtime |
|---|---|
| one waker that does nothing | a real `Waker` per task; the OS wakes the thread when a socket is ready |
| spins on `Pending` | sleeps on `Pending`, costing zero CPU while waiting |
| two futures, hard-coded | a queue of thousands of tasks, `spawn` to add one |
| one thread | a pool of threads stealing tasks — the reason futures need `Send` |

In `tokio` the same program is `#[tokio::main] async fn main()` plus `tokio::join!(a, b)`. The shape
does not change, and now you know what's under it.
